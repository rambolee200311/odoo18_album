直接上传部分可以独立开发和验证，但关闭材料必须明确区分：

## 2. 来源 Resolver 契约

### 2.1 Resolver 入口

CC-02 必须提供一个由业务动作调用的来源解析入口。入口的职责是：

- Resolver 只能由 CC-02 的“从记录创建 Page”和“向既有 Page 添加媒体”业务动作调用；
- CC-03、CC-04、CC-05 不得直接调用 Resolver；
- Resolver 的调用约定（模型方法、辅助类或 Python 函数）由 CC-02-T01 在 IHR 中冻结，调用方只能通过 IHR 登记的入口访问；
- 返回类型必须是 Odoo Recordset 或 CC-02 在 IHR 中冻结的稳定数据结构，不允许返回可被调用方随意修改的原始 dict；
1. 接收已配置的 Source Config、来源记录标识和当前操作上下文；
2. 重新调用 CC-01 的 Source Config 字段校验接口；
3. 使用 Registry 获取配置指向的模型；
4. 使用普通用户权限读取来源记录，不以 `sudo()` 替代来源记录权限；
5. 通过运行时字段名访问已验证的 Many2many 附件字段；
6. 返回经过权限和配置校验的 `ir.attachment` Recordset 及来源追溯信息。

Resolver 不负责：

- 创建 Page 或 Item；
- 直接上传；
- Portal 授权；
- 自动同步来源记录的新附件；
- 绕过来源模型或字段 ACL。

### 2.2 Resolver 输入和输出

| 项目 | 契约 |
|---|---|
| 输入配置 | 一个启用的 `wd.evidence.album.source.config` |
| 输入记录 | 一个当前用户有权读取的来源模型记录 ID；具体模型由配置决定 |
| 输入上下文 | 当前用户、目标 Album/Page、事务上下文 |
| 输出附件 | 目标来源记录字段当前值中的 `ir.attachment` Recordset |
| 输出追溯 | `source_model`、`source_record_id`、`source_field_name` |
| 空值 | 来源字段为空时返回空集合，并由调用方产生明确业务错误；不得创建空附件 Item |
| 多记录 | CC-02 V1 冻结为 Resolver 接收单一来源记录；调用方需要处理多条记录时逐条调用 Resolver，Resolver 不自行遍历 |
| 权限失败 | 返回项目标准业务错误；不得返回成功形状的空结果 |
| 配置失败 | 返回明确配置错误；不得继续读取未验证字段 |

Resolver 的接口形状必须在 IHR 中登记，CC-02 后续任务只能复用该入口，不得建立第二套动态字段解析逻辑。

### 2.3 Resolver 校验

每次使用配置前必须重新确认：

- Source Config 存在且 `active=True`；
- `model_id` 仍指向存在的模型元数据；
- 目标模型当前已加载到 Registry；
- `field_name` 仍存在于目标模型；
- 字段 `ttype="many2many"`；
- 字段 `relation="ir.attachment"`；
- 当前用户可以读取来源记录和目标字段；
- 来源记录 ID 属于目标模型；
- 返回的附件属于实际字段值，而不是通过名称、扩展名或附件 ID 猜测。

配置失效、模型未加载、字段被删除或关系改变时，必须显式失败并记录可定位错误。具体错误类型由 CC-02-T01 在 IHR 中冻结：未启用配置、模型未加载、字段删除或关系改变返回 `UserError`；来源记录无权访问由 Odoo 权限层返回 `AccessError`；错误消息模板必须在 IHR 中登记。

### 2.4 允许列表和安全边界

- 只有已保存且已启用的 Source Config 才能作为合法来源；
- `ir.model.fields` 的候选发现不等于来源自动暴露；
- Resolver 不得遍历目标模型所有 Many2many 字段；
- Resolver 不得接受调用方任意传入的模型名/字段名作为配置替代；
- Resolver 不得以 `sudo()` 读取来源记录后再返回给无权用户；
- 来源模型名和字段名只能作为配置及 Item 快照使用，不得成为 Portal 授权依据；
- 生产模块不依赖任何 `wd_qooling.*` 或具体来源模块。

## 3. 标题和描述映射契约

### 3.1 映射来源

标题和描述映射只用于“从记录创建 Page”时生成初始值：

- 优先使用 Source Config 中已配置且已通过校验的 `title_field_name`；
- 优先使用 Source Config 中已配置且已通过校验的 `description_field_name`；
- 未配置 `title_field_name` 或 `description_field_name` 时不得自动推导字段，必须拒绝从记录创建 Page；
- 已配置字段读取为空时保留空值；如果结果不满足 Page 必填约束，创建动作必须明确拒绝；
- 当前已确认的规则是：未配置映射字段即拒绝，不选择 `name`、`display_name` 或其他隐式字段。

### 3.2 映射校验和读取

- 标题/描述字段必须属于 Source Config 指定的同一模型；
- 字段必须存在且当前用户允许读取；
- 读取结果必须按以下边界安全转换为 Page 可保存的文本：Char/Text 直接保存，不裁剪、不转义；Many2one 保存 `display_name`；Selection 保存 `value` 而不是 `label`；其他字段类型若不在 Source Config 允许的字段类型列表中，配置保存时必须拒绝；
- 已配置字段读取为空时按业务字段语义保存空值；未配置字段时按 TDD-Q-002 决策拒绝，不得把 Python/ORM 异常当作标题；
- 不保留原始 HTML，Page 保存时不做二次转义；
- 映射字段读取失败时，创建 Page 必须明确失败或按上游确认的降级规则处理，不得静默吞错。

### 3.3 用户覆盖和解绑

- 自动填充的 Page `title` 和 `description` 在创建前可以被用户覆盖；
- Page 保存后只保存普通字段值，不保存与来源记录的持续绑定；
- 后续修改来源记录的标题/描述不得自动修改 Page；
- 后续修改来源附件字段不得自动新增或删除 Item；
- `source_model`、`source_record_id`、`source_field_name` 只写入 Item 追溯快照，不作为 Page 的持续关系。

## 4. 媒体合法性和完整性契约

### 4.1 统一校验入口

CC-02 必须提供统一的媒体合法性校验入口，来源采集和直接上传都必须调用它。入口至少接收：

- `ir.attachment` 记录或待创建附件元数据；
- 当前用户；
- 目标 Album；
- 可选来源记录和 Source Config；
- 事务上下文。

入口输出：

- 可接受的标准化媒体类型：`image` 或 `video`；
- 校验通过的附件；
- 失败时的明确业务错误。

来源采集和直接上传不得分别实现两套 MIME、扩展名或内容校验。

### 4.2 允许的媒体类型

只接受以下内容：

| 媒体类别 | 允许格式 |
|---|---|
| 图片 | JPG、JPEG、PNG |
| 视频 | MP4 |

必须同时满足：

- MIME 与扩展名一致；
- 内容可读性校验通过；
- 能据此可靠识别 `media_type`；
- 附件存在且内容非空；
- 不根据扩展名单独猜测媒体类型。

必须拒绝：

- 其他扩展名或 MIME；
- MIME 与扩展名不一致；
- 内容为空；
- 内容无法读取或无法识别；
- 来源记录/字段无权访问；
- 已在目标 Album 中存在的同一附件；
- 来源配置失效或来源字段不合法。

具体内容解析库和实现方式不在本契约中指定，但验证结果必须能证明不是仅凭扩展名放行。

内容可读性校验的实现约定：

- JPG/JPEG/PNG 使用 Python 标准库或项目已确认的图像库读取文件头，确认文件可以打开；
- MP4 读取文件头的 `ftyp` box，确认文件结构可识别；
- 不使用 ffmpeg 或视频转码；
- 校验失败的附件不得创建 Item，也不得调用 `ir.attachment` 的媒体预览；
- 具体库选择由 CC-02-T03 在 IHR 中冻结，但不得引入不在项目依赖白名单中的库。

### 4.3 Item 创建一致性

创建 Item 时必须满足：

- `page_id` 属于目标 Album；
- `album_id` 由 `page_id.album_id` 派生，不由调用方独立决定；
- `source_type="record"` 时，来源模型、来源记录 ID、来源字段名全部保存；
- `source_type="upload"` 时，来源模型、来源记录 ID、来源字段名全部为空；
- `attachment_id` 指向通过统一媒体校验的附件；
- `media_type` 与附件实际内容一致；
- `availability_state` 初始为 `available`；
- 事务失败时不留下孤立附件、半成品 Item 或无法追踪的关系；来源型 Item 失败时不创建附件并回滚 Page/Item，上传型 Item 失败时回滚本次创建的附件，复用已有附件时不得删除该附件；具体回滚策略由 CC-02-T04/T06 在 IHR 中冻结；
- 数据库唯一约束和业务提前检查共同保护 `(album_id, attachment_id)` 唯一性。

## 5. 从记录创建 Page 契约

### 5.1 输入

- 一个已启用并通过重新校验的 Source Config；
- 一个当前用户有权读取的来源记录；
- 一个目标 Album；
- 可选的标题/描述覆盖值；
- 可选的目标 Page 创建上下文。

### 5.2 行为

该业务动作必须在一个明确事务边界内。事务边界使用 Odoo ORM 的标准 `@api.model` 方法和单一数据库事务；不得使用嵌套事务或手动 `commit()`。跨多个 ORM 写入时，所有写入必须在同一个方法调用中完成，由 Odoo 事务管理器统一提交或回滚：

1. 校验 Album 可编辑且目标用户有权操作；
2. 通过 Resolver 读取来源附件；
3. 通过标题/描述映射生成初始 Page 值；
4. 对每个候选附件执行统一媒体校验；
5. 创建 Page；
6. 创建来源型 Item；
7. 保存来源追溯快照；
8. 返回可继续编辑的 Page。

失败时必须按事务语义回滚 Page、Item 和本次新建关系，不留下成功形状的部分结果。

### 5.3 结果

- Page 属于指定 Album；
- Page 内只包含本次显式选择并通过校验的附件；
- 来源记录新增附件不会自动出现在已创建 Page；
- 来源记录删除或修改不会自动修改已创建 Page；
- 用户可以继续编辑 Page 标题、描述和排序；
- Page 不保存来源记录的持续关系；
- Item 保存创建时的来源模型、记录 ID 和字段名快照。

### 5.4 空来源和重复附件

- 来源字段为空时不得创建空附件 Item；
- 如果来源记录包含多个附件，必须逐个校验并明确处理结果；
- 任意附件失败时，不能静默跳过并伪装为完整成功；
- 同一附件已存在于目标 Album 时必须拒绝重复关系；
- 重复错误必须转换为用户可理解的业务错误，不暴露 PostgreSQL 原始异常。

## 6. 向既有 Page 添加来源媒体契约

### 6.1 输入和权限

- 目标 Page 必须属于目标 Album；
- 目标 Album/Page 必须对当前用户可写；
- Source Config 必须启用且重新校验通过；
- 来源记录必须由普通权限读取；
- 只能选择当前来源字段中的附件。

### 6.2 行为

业务动作必须：

1. 校验 Page/Album 归属；
2. 调用 Resolver；
3. 对用户选择的附件调用统一媒体校验；
4. 检查整个 Album 的附件唯一性；
5. 创建来源型 Item；
6. 保存来源追溯快照；
7. 复用 CC-01 §3.3.4 建立的 Item 模型可用性刷新方法，刷新 Item 可用性状态。

该动作不得：

- 自动同步来源字段中未选择的附件；
- 修改 Page 的来源关系（Page 不保存来源关系）；
- 删除或修改原始附件；
- 绕过 ACL/Record Rule；
- 允许跨 Album 的 Page 或 Item。

## 7. 直接上传契约

### 7.1 上传语义

直接上传创建的附件是独立的 `ir.attachment`，不绑定业务单据：

- `source_type="upload"`；
- `source_model`、`source_record_id`、`source_field_name` 为空；
- 附件不设置业务单据的 `res_model`/`res_id` 关系。如果未来需要设置，必须先回到 SRS 修订并更新 TDD，不能在 CC-02 中自行决定；
- Item 仍引用该附件，不复制附件内容；
- 删除 Item 不删除附件；
- 原始附件删除后 Item 按 CC-01 生命周期规则保留并变为不可用。

### 7.2 上传事务

上传流程必须保证：

1. 目标 Page/Album 权限先于附件持久化检查；
2. 上传内容通过 Odoo 标准 `ir.attachment` 创建流程接收，并通过统一媒体校验；不自定义文件接收机制；如果使用 Odoo 标准 widget，必须在 CC-02-T06 的 IHR 中确认与统一校验入口的对接方式；
3. 创建附件和 Item 使用同一明确事务边界；
4. Item 创建失败时回滚本次创建的附件，或留下可追踪且符合项目清理策略的结果；
5. 不产生无法关联到 Page/Item 的半成品附件；
6. 重复附件规则仍适用于同一 Album；
7. 错误向用户呈现明确业务信息，不返回成功形状的空 Item。

### 7.3 上传输入限制

- 只接受 JPG/JPEG/PNG/MP4；
- MIME、扩展名和内容可读性必须一致；
- 空文件、损坏文件和无法识别内容拒绝；
- 上传不得通过文件名推断并跳过内容校验；
- 资源大小和请求限制若上游已有明确规定必须遵守；若上游未给出具体数值，不在本 CC 擅自新增业务阈值。

## 9. 关闭材料清单

对应 CC-02-T07。每类材料必须说明覆盖范围、证据位置、未验证项和阻塞项。

### 9.1 IHR — Interface Handover Record

至少记录：

- Resolver 入口的输入、输出和错误语义；
- Source Config 校验接口的调用约定；
- 标题/描述映射输入、输出和覆盖规则；
- 统一媒体合法性校验入口；
- 从记录创建 Page、向既有 Page 添加媒体、直接上传的业务动作入口；
- 来源型/上传型 Item 的字段约定；
- 事务边界、重复附件错误和权限错误语义；
- CC-03 及后续 CC 可以消费的稳定字段和接口；
- TDD-Q-008 验证模型、字段、权限和替代范围。

### 9.2 ATR — Automated Test Record

至少覆盖以下测试类型，不要求在本契约中写具体测试代码：

- Resolver 动态模型/字段读取；
- Source Config 重新校验和停用拒绝；
- 普通权限读取来源记录；
- 标题/描述映射和用户覆盖；
- MIME、扩展名、内容可读性和空附件拒绝；
- 来源型/上传型 Item 创建；
- 重复附件、跨 Album 和无权限拒绝；
- 事务回滚及附件清理；
- Item 删除不删除附件；
- TDD-Q-008 替代验证或真实集成验证。

ATR 记录执行了哪些测试类型、结果、证据位置和失败项，而不是测试代码本身。ATR 不要求写具体测试代码；测试代码由后续独立测试任务编写。

### 9.3 HVR — Human Verification Record

至少人工或用户辅助验证：

- 配置选择/启用和明确错误提示；
- 从来源记录创建 Page；
- 标题/描述自动填充与覆盖；
- 来源附件选择和重复提示；
- 直接上传图片/视频；
- 非法类型、空文件和无权限来源的 UI 错误；
- 删除 Item 后原始附件仍存在；
- TDD-Q-008 阻塞时来源部分和上传部分的边界。

证据至少包含截图、实际步骤、账号/角色、时间、代码基线和结果。Agent/Tool 观察不得冒充正式人类 HVR PASS。

### 9.4 FR — Feature Record 草稿

FR 至少包含：

- 已完成的来源 Resolver、媒体校验、来源 Item、上传 Item 范围；
- TDD-Q-008 的验证环境和结论；
- 直接上传是否独立完成；
- 已验证、未验证、被阻塞的功能列表；
- TDD-Q-002 的决策状态；
- 遗留问题和技术债；
- CC-03 进入所需的硬门禁确认。
